# 安全机制与部署边界

本文说明当前实现的数据访问、风控及部署前提。漏洞报告与维护范围见 [安全策略](../SECURITY.md)。

## 订单访问与隐私

- 商品订单号使用 `AS` 加 20 位安全随机字符，充值编号增加 `R` 前缀。随机编号降低猜测风险，但不代替访问权限验证。
- 商品查询密码由购买人设置，至少 8 位、最多 72 个 UTF-8 字节，以 bcrypt（成本参数 12）保存哈希。应用不将原密码写入网址、后台响应、发货邮件、卡密下载或浏览器存储。
- 公共查询先验证滑块，再返回订单摘要；读取详情与发货内容还需该订单密码。有效登录会员可以访问本人订单，不能仅凭登录状态读取其他会员的订单。余额充值订单始终要求本人登录。
- **邮箱查询不验证邮箱所有权。** 知道某个邮箱并通过验证码的人可看到关联商品订单的商品、编号、时间、金额与状态。摘要不包含卡密、联系邮箱、账号标识或后台备注。运营者应根据业务隐私要求决定是否接受这一查询方式。

`/order` 只提供查询入口，验证后进入独立结果页。两类短期凭证的权限不同：

| 凭证 | 有效期 | 绑定范围与用途 |
|---|---|---|
| 列表查询凭证 | 10 分钟 | 绑定客户端 IP 与服务端查询条件，读取摘要、筛选与分页；出现在结果页的 `ticket` 参数中。 |
| 订单访问凭证 | 30 分钟 | 绑定单个订单，读取详情、支付信息与支付状态；创建订单或验密后签发，通过请求头提交，不绑定 IP 或登录会话。 |

凭证使用安全随机值，Redis 以其 SHA-256 摘要作为索引保存授权数据。订单访问凭证持有者在有效期内可访问该订单；退出账号或账号改密不会立即撤销已签发的订单凭证。不要分享凭证、完整结果链接或包含它们的日志。Redis 限流或凭证服务异常时，订单接口拒绝请求，不降级为匿名放行。

浏览器 `localStorage` 保存成功查询过的最近 3 个去重邮箱，可逐个删除；不缓存订单号或查询密码。`sessionStorage` 暂存单订单访问凭证和返回列表链接。修改本地缓存不能绕过服务端鉴权；这些可由页面脚本读取的数据仍受浏览器环境、扩展与 XSS 风险影响。

## 登录、后台与反滥用

用户与管理员访问均检查有效会话、账号状态和会话版本。账号改密或封禁后，后续会话验证会拒绝旧版本；这不等于撤销上文的订单访问凭证。OPERATOR 负责商品与发货，ADMIN 可管理用户和财务，SUPER_ADMIN 可修改系统设置。

新设置的用户密码至少 8 位，管理员密码至少 12 位，均最多 72 个 UTF-8 字节；现有账号登录保留兼容。密码重置凭证绑定签发时的账户版本，Redis 仅以令牌摘要索引保存授权。成功改密或封禁撤销此前签发的重置链接；不同链接并发提交也只能有一次改密成功。升级前签发的旧格式链接失效，需要重新申请。

自定义 API 写入及登录/退出请求要求 `Origin` 精确匹配 `NEXTAUTH_URL` 的 origin；缺失、`null`、兄弟子域、不同协议/端口均拒绝，不以客户端 Host 或转发头推断可信来源。提供 `Sec-Fetch-Site` 时必须为 `same-origin`。脚本调用也需显式填写正确 Origin，但这不代替登录或权限校验。只有支付宝/微信两个精确回调路径豁免此检查，仍必须通过支付签名与业务校验；定时任务 GET 继续验证 Bearer 凭据。

页面使用每次请求随机生成的 CSP nonce，Next.js 启动脚本携带相同 nonce；生产环境禁用未授权内联脚本、内联事件和 eval，限制连接为本站，禁用对象、嵌入和外部表单提交。样式仍允许 inline 以兼容 React，图片允许 HTTPS、data 和 blob 以支持商品及支付二维码。全部 HTML 动态渲染并设置 private/no-store，避免缓存复用 nonce；因此不能依赖 CDN 缓存 HTML。开发环境额外允许 eval 与 WebSocket，用于热更新。

滑块图片在服务端生成，答案坐标不直接返回，令牌绑定 IP、5 分钟有效并在业务请求中一次性消费。它是基础防自动化措施，不证明用户身份，也不能阻止所有识图或分布式攻击。

订单查询限流采用 Redis 原子计数：

- 首次查询：每 IP 每分钟 10 次；结果页分页与筛选：每 IP 每分钟 60 次。
- 密码验证：每 IP＋订单每 10 分钟 10 次，并叠加每 IP 每 10 分钟 50 次。
- 详情、支付信息与支付状态分别限流，轮询不消耗密码验证次数。

登录、注册、回调和上传也有独立限制。限流效果依赖可信客户端 IP 的配置；多人共用网络可能共用额度，分布式请求仍需代理层或运营侧风控。

外部支付的商品订单还受待付库存额度保护：每个账号、邮箱及可信客户端 IP 分别最多 3 笔待付款订单、合计 100 件，由 `MAX_PENDING_ORDERS` / `MAX_PENDING_QUANTITY` 配置（1–10000 的整数）。在预留库存的串行化事务内校验，跨商品、并发请求也受限制。付款或取消后释放额度；过期订单由每分钟任务取消后释放。支付链接创建失败的订单仍占用额度直至取消/过期，避免网络超时后实际付款被误取消。余额支付即时结算，充值不占商品库存，均不纳入该额度。没有可信 IP 时仅执行账号和邮箱额度，`direct`/`unknown` 不作为个人身份；生产部署应配置可信代理，邮箱可替换这一事实仍要求运营侧防范分布式囤单。

## 支付、库存与通知

支付方式需要同时具备有效配置和后台启用状态。支付宝/微信回调校验签名、商户、通道、金额和订单状态；数据库唯一流水与事务保障重复回调不会重复扣款、入账或发货。余额变动、库存预留和发货使用数据库串行化事务处理。

支付回调流式读取上限为 16KB（包括没有 Content-Length 的请求），重复参数拒绝处理。隔离测试覆盖实际回调入口、错误金额/通道/签名、重复回调、跨订单流水复用与链上匹配；不能据此替代运营方真实收款账户的小额联调。

USDT 自动收款仅开放 TRC20，使用持久化报价、整数微单位金额和已确认链上转账，交易哈希不能重复认领。ERC20 自动收款未实现；无报价的历史付款、错误金额、超时付款等异常需要人工核对，上线前应完成运营方账户的小额联调。

余额退款返还站内余额；外部支付退款需要先在支付平台人工执行，后台只登记结果。邮件与 Telegram 是可选通知，通知失败不会重做入账或发货，也没有自动补发保证。配置的邮件服务可能接触明文发货卡密，通知服务可能接触订单信息；运营者应限制接收人并妥善保管服务凭据。

SMTP 发信使用 TLS 或强制 STARTTLS，并检查服务器证书；`npm run mail:check` 仅验证连接和认证，不发送邮件。密码重置发送失败时清理本次生成的令牌；账号认证成功不等于收件箱实际收到邮件，投递仍需实际收件确认。

图片上传需要管理员认证，限制额度、文件大小和解码像素，并验证实际图片格式、重新编码去除附加内容与元数据。配置 Cloudinary 后，商品图片和上传的微信群二维码会存储到该服务。微信群二维码配置仅允许 SUPER_ADMIN 修改；固定入群页面公开展示当前有效群码，过期时间由管理员填写，不代表应用能自动续期微信邀请。维护方式见 [交流群入口说明](community/README.md)。

微信客服、Telegram 和微信群统一由 SUPER_ADMIN 在 `/admin/contact` 配置。公开客服接口只返回白名单联系字段并禁止缓存；微信客服文字虽然不在二维码弹窗中展示，仍属于公开接口数据，不能用作后台私密备注。群邀请与个人客服二维码分别维护。前台邮件联系入口已移除，SMTP 发信与密码重置继续独立工作。

卡密导入每批最多 500 条、每条最多 10000 字符，请求体最多 2MB，每位管理员每小时最多 20 批。密钥派生结果只在进程内按当前密钥缓存，现有 AES-GCM 格式不变，避免读写每条卡密时重复执行昂贵的派生计算。邮件和 Telegram 的动态文本均转义后插入 HTML。

## 部署、密钥与数据保留

- 公网入口使用 HTTPS；使用 Cloudflare 时，源站也应配置 TLS 并使用 **Full (strict)**。仓库默认 Nginx 仅监听 HTTP，不能视为完整的公网 TLS 配置。
- 应用、PostgreSQL 和 Redis 端口只向受信网络开放。仅在代理覆盖 `X-Real-IP`、且访客不能绕过代理直连应用时启用 `TRUST_PROXY=true`。Cloudflare 场景需验证源站来源并正确配置受信代理 IP。
- **`TRUST_PROXY=false` 时，应用将所有请求识别为 `direct`。** 此时 IP 限流共用额度，验证码/查询凭证的 IP 绑定无法区分实际访客；默认示例不是生产客户端 IP 配置。不直接信任用户传入的 `CF-Connecting-IP` 或 `X-Forwarded-For`。
- 缺失必要密钥时服务拒绝启动。数据库、认证、卡密加密与定时任务使用独立随机凭据；首次管理员密码没有内置默认值。不要将 `.env`、数据库备份、真实卡密、凭证或运行日志提交到仓库。
- 卡密使用 AES-256-GCM 加密，持有服务端加密密钥的运营者可解密；这不是端到端加密。限制数据库、密钥、后台和备份访问，备份恢复后验证库存与资金一致性。更换加密密钥前必须重新加密已有卡密。
- 默认订单有效期 10 分钟、清理阈值 90 天；清理只处理符合条件且没有敏感关联记录的取消订单，资金流水和已售卡密不会按该阈值自动删除。数据保留与销毁需要运营者另行制定。

数据库升级的备份及不兼容迁移要求见 [README 的升级章节](../README.md#升级备份与迁移)。发现密钥泄露时，撤销第三方凭据、更新受影响密钥，按所持数据核对影响范围；不要通过清空生产数据库或直接更换卡密加密密钥掩盖问题。

## 验证与依赖维护

CI 检查生产构建、单元与隔离集成测试、HTTP 冒烟、当前文件敏感信息扫描、完整检出中所有可达提交的作者/提交者邮箱和依赖审计。`check:secrets` 不扫描历史文件；`check:history` 检查提交元数据且拒绝浅克隆，两者都不代表完整历史内容扫描。邮箱检查仅输出提交位置，不打印地址。测试通过只覆盖已验证的路径，不证明第三方收款已完成真实联调，也不代表不存在漏洞。历史停用凭据不得用于新部署。

将私有仓库改为公开之前，还应检查远程分支、标签、PR 保留引用、发布附件和媒体内容。改写主分支不会自动删除托管平台保存的已关闭 PR 引用或旧对象；此类残留需要平台支持处理或迁移到只包含已清理历史的新仓库。不要将扫描范围仅为本地分支的结果当作整个托管仓库已清理。

依赖审计告警需要结合依赖路径、运行产物和可达输入评估；构建工具漏洞也应安排修复。验证命令及测试环境要求见 [贡献说明](../CONTRIBUTING.md)。
